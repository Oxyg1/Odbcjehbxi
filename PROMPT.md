## 3. Направление 2: проблемные блоки

### 3.1 Главный блок — `on_callback` (18 840 строк, 411 веток)

Единственный `CallbackQueryHandler` без `pattern=`, то есть **каждое нажатие
любой кнопки** линейно проходит цепочку из 411 условий. Специализированные
роутеры вызываются в конце (строка ~50 400), поэтому кнопка экспедиции сначала
проверяет ~18 600 строк чужих условий.

Что внутри монолита (разобрано по веткам):

```
админка          67 веток  2 478 стр   ← выносится первой, она изолирована
стаи/война       40 веток  1 428 стр
казино           14 веток    872 стр
дуэли             6 веток    472 стр
гача              5 веток    439 стр
NFT              10 веток    427 стр
соседи/друзья     7 веток    359 стр
комар             1 ветка     236 стр
```

**Как разбирать — по одной группе за раз:**

```python
# роутеры регистрируются ДО общего on_callback
app.add_handler(CallbackQueryHandler(admin_router,  pattern=r"^(admin|ca_|cs_)"))
app.add_handler(CallbackQueryHandler(gacha_router,  pattern=r"^gacha_"))
# ... по мере переноса ...
app.add_handler(CallbackQueryHandler(on_callback))   # ВСЕГДА последним
```

Пока группа не вынесена — она продолжает работать в старом `on_callback`.
Ничего не ломается разом, можно остановиться после любой группы.

**Порядок выноса:** админка (изолирована, 2 478 стр) → гача (самая
популярная) → NFT → казино → стаи → дуэли → остальное.

### 3.2 Гонки в экономике

Атомарный `db_coins_delta` вызван **4 раза**, а read-modify-write —
сотни раз. При этом `db_save` пишет обратно **всю строку** (137 колонок),
поэтому два параллельных обработчика затирают друг другу не только монеты,
а уровень, XP, инвентарь и кулдауны.

Правило: **любое изменение числового поля — атомарным SQL.**

```python
# ❌
f["coins"] = f.get("coins", 0) - price
await db_save(f)

# ✅
new_balance = await db_coins_delta(uid, -price)
if new_balance is None:
    return await q.answer("Недостаточно КваКоинов", show_alert=True)
```

Начать с денежных путей: казино, гача, магазин, переводы, `successful_payment`.

Плюс: 814 прямых `aiosqlite.connect` против 13 использований написанного
пула `_DBPool`. Свести к одному слою доступа.

### 3.3 Ошибки не видны

818 из 1004 обработчиков — молчаливый `except: pass`. Это причина, по которой
непонятно, что сломано. Заменить на `logger.exception(...)` с контекстом.

`except: pass` допустим только в двух случаях: удаление уже удалённого
сообщения и ответ на протухший callback.

Плюс: 24 отладочных `logger.error("🐛 [EXP DEBUG] ...")` — понизить до `debug`,
они топят настоящие ошибки.

### 3.4 Мелкие баги — чинятся быстро

1. `/gift` зарегистрирована дважды → `cmd_gift_friend` **никогда не вызывается**
2. `/nft_list` зарегистрирована дважды
3. `raid_get_active_guard` — два определения (L8167, L10636), побеждает второе
4. `_raid_calc_steal` — два определения (L8180, L10653)
5. `friend_get` — два определения (L13287, L14038)
6. L3521: `int(os.getenv("NFT_CLUB_CHAT_ID", ...))` — результат не присваивается
7. Требование Python 3.12+ нигде не зафиксировано

### 3.5 Секреты

В `frog_bot.py` живой токен бота и живой Telegram WebApp `initData` как
fallback-значения `os.getenv`. Я ротирую сам, но код должен быть готов:
только `os.environ["X"]` без fallback, загрузка через `python-dotenv`.
**`frog_bot.py` не коммитить в git, пока в нём есть секреты.**

в 8 местах. При этом 28% активных игроков верификацию уже прошли.

Что стоит сделать:

- Поднять `/portfolio`, `/giftcheck`, `/giftfloors`, `/checkgroup` из

- Без гифта играть можно, лягушка дефолтная
