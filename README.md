# ton-vanity

Генератор TON-кошельков (по умолчанию **v5R1** - нынешний стандарт Tonkeeper; также v4R2 через `--wallet v4`; workchain 0, mainnet), который перебирает ключи, пока адрес не закончится на нужную строку (по умолчанию `pulse`).

```
cargo build --release          # собирается под ваш CPU (target-cpu=native)
./target/release/ton-vanity    # ищет ...pulse
./target/release/ton-vanity --suffix pulse --nocase     # без учёта регистра (в ~20 раз быстрее)
./target/release/ton-vanity --wallet v4                 # кошелёк v4R2 вместо v5R1
./target/release/ton-vanity --subwallets 64             # см. ниже
./target/release/ton-vanity verify <seed_hex> [v5|v4]   # пересчитать адрес по seed
```

Результат печатается и дописывается в `found.txt` (права 0600, файл в .gitignore): адреса EQ/UQ, публичный ключ, seed и секретный ключ.

## Как устроена оптимизация
- Окончание адреса — это последние 6·k бит (хвост хеша + CRC16), поэтому в цикле сравнивается число, строка base64 не строится.
- Проверяются сразу два варианта адреса (bounceable `EQ…` и non-bounceable `UQ…`): CRC линеен, его считают один раз, вариант флага добавляется XOR-константой. Это вдвое больше шансов на каждый ключ.
- Хеш адреса считается тремя вызовами `compress256` по готовым шаблонам блоков, без аллокаций и паддинга.
- Ключи: ChaCha20 (затравка из ОС) → SHA-512 → умножение базовой точки по предвычисленной таблице (curve25519-dalek). Потоки независимы, общий счётчик обновляется раз в 512 ключей.
- Каждый найденный результат перепроверяется медленным эталонным путём.

## Важно
- Ключ - это 32-байтный seed, **мнемофразы нет** (генерация через мнемонику в сотни раз медленнее из-за PBKDF2). Кошелёк используется через библиотеки (`@ton/ton`, `tonsdk` и т.п.) по seed/секретному ключу, а не импортом по 24 словам.
- `--subwallets N` перебирает на каждый ключ N субкошельков (v4R2: wallet_id 698983191 + j; v5R1: номер субкошелька j, wallet_id = 2147483409 XOR j, до 32768). Это ускоряет поиск, но wallet_id будет нестандартным; его нужно передавать в библиотеку при создании кошелька. Без флага используется стандартный wallet_id.
- Адрес с регистром `pulse` встречается примерно в 1 из 5·10⁸ проверок; время зависит от числа ядер.

## Версия для видеокарт NVIDIA (CUDA) — каталог `cuda/`

```
cd cuda
nvcc -O3 -arch=native -o ton_vanity_cuda ton_vanity.cu     # нужен CUDA Toolkit (11.8+ для RTX 40xx)
./ton_vanity_cuda --suffix pulse
```
Опции те же (`--suffix`, `--nocase`, `--subwallets N`, `--out`), плюс `--blocks N` для подбора загрузки. Если `-arch=native` не поддерживается вашим nvcc, укажите архитектуру явно: `-arch=sm_89` (RTX 40xx).

- Ключи совместимы с CPU-версией: это обычные 32-байтные seed (SHA-512 → clamp → ed25519), мнемоники нет.
- Seed для ключа номер *n* = SHA-512(секретная случайная затравка запуска ‖ n), затравка берётся из ОС, поэтому seed непредсказуем.
- Умножение базовой точки идёт по таблице (32×8 точек, строится на хосте), одна инверсия поля на 8 ключей (метод Монтгомери).
- Каждая находка перепроверяется на CPU перед выводом. Независимо проверить результат другим кодом можно так:
  `./target/release/ton-vanity verify <seed_hex> [wallet_id]` (Rust, dalek + sha2) — должны получиться те же адреса.
- Если Windows перезапускает драйвер из-за долгих ядер (TDR), уменьшите `--blocks`; длина запуска сама подстраивается под ~0.25 с.

### Как это проверено
Из-за отсутствия GPU при разработке весь вычислительный код (`tv_core.h`) компилируется и обычным C++ и прогонялся на CPU, включая эмуляцию самого ядра поиска (`cuda/test_cpu.cpp`: `g++ -O2 -o test_cpu test_cpu.cpp && ./test_cpu`). Сверка с эталонами: RFC 8032, адрес `tonsdk`, 30 000 случайных ключей против `pynacl`, найденные адреса против `tonsdk`. Сами запуск ядра и работа с памятью GPU (`ton_vanity.cu`) на реальной карте не запускались.


CUDA-версия пока умеет только v4R2.
