# От исследования к коду

Проект вырос из аналитической записки «Автономная покупка подарков в Telegram
Market: стратегия создания юзербота на основе MTProto API». Здесь — что из
выводов записки реализовано, где и почему, а что сознательно не сделано.

## Основные выводы записки

1. Официального API для Telegram Market нет; Bot API не умеет ни смотреть
   каталог подарков, ни покупать из него. Значит — юзербот поверх MTProto.
2. Telegram Mini Apps как «бэкдор» не работают: каталог не является публичным
   ресурсом, каждый запрос из TMA подписан `initData`, а эмуляция кликов по
   WebView хрупка. Событие `DialogPaymentSent` сообщает лишь о состоявшемся
   платеже — для обнаружения лотов оно бесполезно.
3. MTProto — не «бэкдор», а штатный протокол клиентов. MTProxy маскирует
   трафик, но не даёт ни одного дополнительного метода и никаких новых прав.
4. Ключевые методы: `payments.getStarGifts` (каталог),
   `payments.getResaleStarGifts` (вторичный рынок), `payments.sendStarsForm`
   (оплата звёздами).
5. Главные риски — не нехватка методов, а `FLOOD_WAIT`, блокировка аккаунта и
   нестабильность внутреннего API.

## Как это отражено в коде

| Вывод записки | Реализация |
| --- | --- |
| Юзербот вместо Bot API | Telethon, `client.py` — сессия, 2FA, прокси |
| Мониторинг каталога | `market.py: MarketClient.catalog()` — `payments.getStarGifts` с кэшированием по `hash` |
| Вторичный рынок | `market.py: MarketClient.resale()` — `payments.getResaleStarGifts`, `sort_by_price=True`, постранично |
| Фильтрация лотов | `filters.py` — цена, id, название, лимитированность, тираж, остаток |
| Покупка | `purchase.py` — `payments.getPaymentForm` → `payments.sendStarsForm` |
| Обработка `FLOOD_WAIT` | `ratelimit.py: ApiGuard` — сон ровно на запрошенные секунды, пауза для всех вызовов, отказ ждать чрезмерный бан |
| Интервал опроса ~60 с | `runtime.poll_interval` по умолчанию 60 с, значения меньше 15 с отклоняются на этапе валидации конфига |
| Конфигурация: секреты в env, остальное в файле | `config.py`, `.env.example`, `config.example.yaml` |
| Уведомления через отдельного бота | `notify.py` — Bot API `sendMessage`, ошибки доставки никогда не фатальны |
| Docker / VPS-развёртывание | `Dockerfile`, `docker-compose.yml`, `examples/systemd/` |
| Модульная структура (аутентификация, мониторинг, фильтрация, покупка) | `client.py` / `market.py` / `filters.py` / `purchase.py`, связывает `runner.py` |
| Нестабильность API | методы резолвятся через `getattr`; отсутствующий `getResaleStarGifts` отключает вторичный рынок, а не роняет процесс |

### Чего в записке не было, а в коде есть

- **Перепроверка цены.** Записка упоминает, что процесс оплаты многоэтапный.
  Практическое следствие: цена в форме оплаты может отличаться от цены в
  каталоге. `purchase.py` сверяет цену из `getPaymentForm` с потолком и
  отказывается платить, если она выросла.
- **Бюджетные потолки.** Покупка необратима, поэтому есть лимиты на лот, на
  цикл, на всё время работы и резерв баланса; живой режим не стартует без хотя
  бы одного общего потолка.
- **Dry-run по умолчанию.** Ни одна звезда не тратится, пока это не разрешено
  явно (`--live`), причём `DRY_RUN=true` в окружении перекрывает конфиг.
- **Журнал состояния.** `data/state.json` переживает перезапуск: бот не
  покупает одно и то же дважды и не присылает повторных уведомлений.
- **Проверка баланса перед покупкой** — и отказ покупать, если баланс прочитать
  не удалось.

### Что сознательно не реализовано

Записка рекомендует диверсификацию: пул аккаунтов на разных номерах и IP,
автоматическое переключение при бане, случайные задержки «под человека».
Этого здесь нет.

Такие приёмы направлены на обход систем защиты платформы, а не на работу внутри
её лимитов; они превращают риск потери одного аккаунта в риск потери
нескольких. Проект держится противоположной линии: один аккаунт, один
транспорт, честный интервал опроса, точное соблюдение `FLOOD_WAIT` и остановка,
когда сервер явно просит остановиться. Джиттер к интервалу опроса есть, но он
нужен, чтобы несколько экземпляров или перезапуск не били в одну секунду, а не
для маскировки.

Отдельно: `payments.canPurchaseStore` и подобные методы помечены как
предназначенные для официальных приложений — обходить эти ограничения проект не
пытается.

## Практические замечания

- `payments.getResaleStarGifts` запрашивается **по одному gift_id**, поэтому
  вторичный рынок сканируется только для перечисленных в конфиге подарков.
- Лоты вторичного рынка идентифицируются по `slug`, а не по `gift_id`: один и
  тот же подарок существует во множестве пронумерованных копий.
- Цена лота вторичного рынка может быть выражена в TON — такие лоты
  пропускаются, бот платит только звёздами.
- Дробные цены (`StarsAmount.nanos`) округляются вверх, чтобы лот за 99,5⭐ не
  проскочил через потолок в 99⭐.
